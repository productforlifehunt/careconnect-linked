# 交给另一个 AI：全 App 读写核对器检查与修复说明

请先阅读项目的 `AGENTS.md`、`README.md`、`package.json` 和核对器相关代码，再检查并修复**整个 App** 的读写核对器。不要只修当前页面或当前报错，也不要把静态扫描结果当成全 App 运行验证。按项目当前的 React Router 7、Yarn 和既有数据层工作；不要另建路由、笔记存储或元素识别系统。

## 项目里已有的识别与笔记关系

- 页面来自 `src/app/routes.ts` 的 React Router 文件路由；一个仓库也包含按 `__site` 区分的独立子应用。审计范围要包含所有路由、品牌入口、动态路径、表单、弹窗、门户层内容、列表和复用组件。
- 页面注释用 `page|页面路径` 定位，元素注释由 `src/features/inspector/inspect-dom.ts` 与 `src/components/inspector/ReadWriteInspector.tsx` 生成稳定元素键。优先使用构建时注入的 `data-inspector-id`，回退到 React 组件与 DOM 结构锚点；身份不应依赖可变的文案、输入值、CSS 类、源码行号或账号/记录 ID。动态记录路径归一化为 `:id`；固定用途的列表项可以用固定 React key 区分，普通数据行应共享槽位。门户、表单和对话框要有明确且互不冲突的 `data-inspector-scope`。
- 元素另存构建无关 alias，以及可选源码指纹作为辅助证据。旧绑定只能在唯一目标有标签或源码证据佐证时迁移；证据不唯一就报告未识别，不能猜测并把笔记绑到相邻按钮或字段。
- 页面/元素到笔记的绑定存在 WordPress CCT324 的 `a59` JSON `inspectorBindings` 中。只更新当前明确选中的 key；保留 `a59` 里其他元数据、同一笔记的其他页面/元素绑定和其他笔记的绑定。这里的 UI 绑定不是 JetEngine 笔记关系。
- 笔记正文存在 CCT324：`a55` 标题、`a56` 正文、`a58` 手动核对状态、`a60/a61` 笔记关联核对状态与详情、`a62` 版本号。以 `src/integrations/wp-schema.ts` 中已核实的字典映射为准，不猜字段名或选项值。
- 笔记之间的多对多关联存在 REL325。添加/解除一条关系不得替换该笔记的其他关系。只有复制版本时新增的“旧版本 → 新版本”关系使用 REL325 字段 `a55: ["b55"]`（Different version of a note）；普通主题关联不要自动选这个类型。用户决定是否逐条解除关系。复制版本保留原有直接 REL325 关联；不会自动复制原笔记的 `a59` 页面/元素绑定，切换绑定应由研究员在界面明确操作。

## 核对器应如何判断读写逻辑

1. 从每条路由的实际渲染代码开始，沿本地 import 追踪到组件、事件处理器、React Query/source、WordPress 客户端、server action、REST resource 和所用 CCT/REL/字段。表单不仅要检查可见输入，还要检查校验、提交、保存后回读、取消/删除和错误分支。依据真实代码与字典判断读写，不以屏幕文案或旧报告代替。
2. 元素识别读取当前点击目标的真实标签、React 组件、事件处理器、链接、列表槽位、表单作用域及采集到的请求。编辑器的构建期源码标记是提示；核对时必须读取当前实际页面对应的前端源码、被调用的读写辅助函数和字典。不要依赖过期索引或缓存的源码映射。
3. 每项核对都应明确比较三类证据：当前页面/元素注释、它通过 REL325 直接关联的全部笔记（包括版本笔记）、实际代码和数据字典。功能逻辑笔记作为业务基准，不要擅自改写或解除其关联。对于已标记手动核对的内容，未经明确授权不要覆盖。
4. 读写观察器是观察工具。现有集成会在核查模式拦截 `wordpress-client` 的非 GET 请求，并观察其他 fetch、store 操作和 app server function；AI 说明接口还会重新验证研究员身份。不要为了“测试”而让观察器提交真实业务数据，也不要绕开现有研究员权限。
5. 保存笔记时，编辑任一字段都应正确启用保存；显示保存中、成功或失败，并对返回数据执行适当回读。失败、登录态变化、过期元素、缺代码、依赖解析失败或证据不全都必须显示为未完成，不能报告“无冲突”或“全站通过”。

## 必须完成的全 App 检查与修复

- 枚举所有路由和 `__site` 子应用；逐项核对整页绑定、已绑定元素以及未绑定页面。对每个页面梳理真实读取、写入、更新、删除、关系变更和外部服务调用，尤其检查表单、重复列表项、共享组件、门户弹窗和动态记录页。
- 在发布构建中确认 Draftbit 元素标识仍能被识别；同时确认本地预览构建可用。不要编辑 `.draftbit` 生成文件或移除 `vite.config.ts` 里的 Draftbit 插件兼容包装。若工具只能在预览识别、发布后失效，必须定位构建差异并修复后再报告。
- 检查保存和选择笔记时 key 到 CCT324 ID 的映射；验证同页多个相似控件、不同表单、不同站点、动态 ID 页面和重复列表不会串笔记。检查迁移是否唯一且无静默覆盖；改动位置绑定后回读 `a59`，确认既有其他位置和未知元数据仍完整。
- 检查 REL325 新建、复制、编辑、查询和解绑路径：普通关联不得被改成版本关系；版本关系应只在对应的旧/新版本边上写入 `a55=["b55"]`；创建新版本不能丢失源笔记已有关系或自动删除任何边。
- 修复发现的代码问题，而不只生成报告。使用项目已有组件、状态和请求模式。为识别、读写、保存失败/回读及多关联版本行为补充有针对性的测试；测试真实交互时用隔离数据，避免污染用户记录。
- 逐页检查实际预览交互，并运行项目已有的类型检查、相关测试及构建。若发布构建、某路由、账号权限或服务因环境原因无法验证，明确列出未验证的页面和原因；不得用 HTTP 200、空白页面、静态扫描完成或“没有发现问题”替代验证。

## 交付报告

报告检查过的全部路由/子应用、表单与读写端点范围；发现并实际修复的问题；笔记绑定与 REL325 关系是否保持原样；运行过的检查及逐项结果；仍缺少的证据或未能验证的页面。只有覆盖完整且证据齐全的范围才能称为已完成；任何遗漏都要显式标为未完成。
